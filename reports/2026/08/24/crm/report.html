二、安装部署与使用指南

项目定位：Comp AI CRM 是一款面向 AI 代理的 Agentic-first 开源 CRM，核心运行环境为 Bun + Turborepo 单仓库，数据库使用 Postgres，生产部署建议基于 Vercel。

环境要求：Bun 1.3.12、Node >=22、Docker（本地 Postgres 容器）。

本地安装（Quick Start）：

git clone https://github.com/trycompai/crm.git && cd crm
cp .env.example .env          # then fill in the values below
bun install

docker compose up -d          # Postgres on :5432

bun run db:deploy             # apply migrations
bun run db:seed               # optional: a believable pipeline to look at
bun run dev

应用运行于 localhost:3000，API 运行于 localhost:3001。

必需配置（编辑仓库根目录 .env）：

  • BETTER_AUTH_SECRET：运行 openssl rand -base64 32 生成。
  • ALLOWED_SIGN_IN：允许登录的邮箱域名或单个地址，例如 acme.com 或 you@gmail.com；未设置时无人能登录。
  • 至少配置一种身份提供商：GOOGLE_CLIENT_ID/GOOGLE_CLIENT_SECRET（Google OAuth）或 MICROSOFT_CLIENT_ID/MICROSOFT_CLIENT_SECRET（Microsoft Entra），也可登录后在 Settings → SSO 添加自定义 IdP。

DATABASE_URL 已匹配 docker compose 中的 Postgres，无需修改（若自带数据库则替换）。

生产部署：需要三个独立部署（Next.js 前端、NestJS API、agent）加一个 Postgres。三者只需在 DATABASE_URL 和 BETTER_AUTH_SECRET 上保持一致；设置 API_URL/APP_URL 为真实域名，跨子域时增加 AUTH_COOKIE_DOMAIN；向 OAuth 提供商注册回调 https://<your-api-host>/api/auth/callback/google 与 .../microsoft；配置 CRON_SECRET 并用调度器调用 POST /internal/sync/mailboxes 保持邮箱同步。

D2.1 产品设计与创新性（1.2/1.5）

产品理念清晰且差异化鲜明——「Agentic-first CRM」明确将 AI 代理而非人类用户作为 CRM 的一等公民，与 Salesforce/HubSpot 以人工录入为中心的设计范式形成根本区隔。功能设计围绕该理念展开：Agent Builder（对话式构建自定义代理）、事件驱动触发（CRM 事件→任务队列）、事实账本（Fact Ledger，含 AI 事实审核）、AI 丰富化（enrich/research）等模块均为原生 AI 能力，而非在传统 CRM 上修补。差异化方面，开源 + Agentic-first 的组合在当前 CRM 赛道中独树一帜。P1 摘要显示 Agent Builder 的会话式构建体验（builder-runtime、agent-builder-chat）设计精巧，状态机流转与事件流订阅实现了「对话 → 草稿 → 部署」的闭环。扣分点：AI-native CRM 赛道竞争已趋激烈，设计理念的长期护城河尚需验证；部分功能（如网站追踪、多货币）偏常规，创新集中在 Agent 层。

D2.2 架构设计与工程质量（1.6/2）

整体架构优秀：标准 Turborepo monorepo，apps/{agent,api,app} 对应 Agent 运行时（Eve 框架）、API 服务（NestJS）、Web 前端（Next.js），packages/{auth,db,env,telemetry,typescript-config,ui,validation} 抽离共享层，模块解耦充分、依赖方向正确。工程实践达到生产级水准：$transaction 事务、FOR UPDATE 行级锁、幂等键（lockIdempotencyKey）、租约机制（ACTION_LEASE_MS）、状态机校验、审计日志在 agent 调度、Agent 定义生命周期、联系人/交易服务中系统化运用，复刻门槛高。目录结构清晰，12.4 万行代码量与功能复杂度匹配。存在技术债：.agents/skills/install-anti-slop/assets/anti-slop/ 与 tools/oxlint/anti-slop/ 下 dictionary-types.ts、no-widen-then-assert.ts 等文件内容完全重复；saveBuilderDraft（约 200 行）、readCompanyHistory（约 200 行）、revise 等方法过长；apps/api/src/generated/server.ts 为自动生成的 publicProcedure 占位实现，依赖后续替换。另有少量原生 SQL 但均已参数化。综合扣分后落 7–8 档。

D2.3 代码整洁性与规范性（0.8/1）

整体整洁度良好：命名遵循 TypeScript 惯例（组件 PascalCase、函数 camelCase），P1 抽查的 20 余个核心文件均显示职责划分清晰、类型安全（严格模式 + satisfies 断言 + Zod schema），错误处理统一（translate 方法、NotFoundException/ConflictException 区分）。代码风格有强约束：@biomejs/biome + oxlint + 自定义 lint:slop（anti-slop 规则），CI 强制 check-types/lint 通过。注释质量较好，复杂逻辑（幂等、租约、状态机）均有说明。主要扣分：两个目录下的 dictionary-types.ts 与 no-widen-then-assert.ts 完全重复（P1 明确指出"存在代码重复问题"）；多处 service 存在相似逻辑（如 runNow 与 retryRun、业务服务间的批量操作、事务错误处理）可提取公共模块；agent-builder-chat.tsx 主组件逻辑较重。落 7–8 档。

D2.4 安全性（0.8/1）

安全编码实践良好，无高危漏洞。正面证据：Zod schema 广泛用于外部数据运行时验证（builderMessage、streamEvents、webhook payload 等）；权限断言系统化（assertWorkspaceMember、assertCanManage、assertCanRead、assertResourceAllowed）；timingSafeEqual 常量时间比较防时序攻击（crm.ts 通道认证）；分享令牌哈希验证；幂等键防重放（结合 SHA-256 请求哈希）；金额以分（cents）存储避免浮点误差；附件大小/类型限制；域名/邮箱规范化输入清洗；遥测模块采用 allowlist（permitted* 函数）限制上报字段——这一设计体现了数据最小化意识。薄弱点：CI 工作流未集成 Dependabot/Snyk/Trivy 等自动依赖漏洞扫描（auto-pr.yml 虽提及 dependabot 分支但无对应 workflow）；apps/api/src/generated/server.ts 的 publicProcedure 无认证中间件（虽为生成模板，但存在误用风险）；工具脚本 generate_review.py 通过字符串替换嵌入用户内容，未转义存在 XSS 风险（非生产代码）。落 7–8 档。

数据壁垒 部分。README 明确「Company brand data 和 LinkedIn 均来自 Context，同一把 key」——Context 提供企业品牌数据（logo/行业/真实名称）和 LinkedIn 画像反查，属于专有数据集成，构成独特的增强数据源。但项目明确设计为「无任何外部 key 也能运行」（读自有邮件线程/签名块即为最佳证据），Context 数据是加分项而非命脉，因此数据壁垒不构成强制锁定。
网络效应 弱。单租户架构（刻意不设 organizationId）、自托管部署、无插件市场、无社区数据共享协议；agent 为单实例自主运行，用户之间无互动，未观察到任何网络效应机制。
规模效应 弱。单租户、无组织模型，规模扩大不带来明显的成本摊薄或体验提升；反向地，单租户数据隔离设计决定了每个客户独立跑一套 agent，运营成本线性增长。

综合判断：「有一定壁垒但不深厚」档（5–6 分档）。架构理念有认知壁垒（evidence-first 的 agent 设计原则），Context 专有数据提供有限数据壁垒，但网络效应与规模效应缺失，MIT 开源使代码层防御接近于零。

D5.3 切换成本与用户粘性（2 分）— 小分 1.2/2

考察点 评估
迁移成本 中等。CRM 核心资产（联系人、公司、交易、邮件同步记录）存于用户自有的 Postgres，数据导出具备可行性，迁移至其他 CRM 是常规操作而非重写业务逻辑。但 agent 专属资产——证据账本、schedule_recheck 的再检查计划及理由、agent 对每条记录的历史判定——无法导出到任何现成竞品，这些「agent 的运营记忆」一旦放弃即归零。
深度集成 较深。三进程架构（Next.js 前端 + NestJS API + eve agent）+ 邮件同步（Gmail/Outlook 只读前向增量）+ OAuth 授权 + 日历 + tRPC 全栈类型安全 + agent 对话桥（AGENT_BRIDGE_SECRET），用户需配置 Google/Microsoft 应用注册、身份提供商、Postgres、可选的 Redis 与调度器，部署集成工作量明显高于「即插即用」型 SaaS CRM。集成越深，拆解的沉没成本越高。
习惯锁定 中等。agent 自动填充记录、自主安排跟进、在记录页展示推理过程并接受发问——使用越久，用户对「agent 已维护好的事实基线」的依赖越强。但项目仅 3 周龄，用户尚未形成长期组织流程依赖，粘性尚处培育期。

综合判断：「迁移成本中等，有部分粘性」档（5–6 分档）。数据可迁移性强（自托管 Postgres + MIT 开源），但 agent 运营记忆的不可移植性与较深的集成深度提供了中等偏上的留存支撑。

综合判断：「护城河一般，有中等颠覆风险」档（5–6 分档）。当前优势建立在执行速度和理念独特性上，尚无可防御的持久壁垒；大厂与 agent 框架新进入者构成明确的中期威胁。

  4. 集成与可观测性现状（D7.4）：集成能力优于可观测性——tRPC contracts 定义完整（conversations.contracts.ts、agents.contracts.ts 等 zod schema 全覆盖），REST 路由覆盖认证回调、OAuth、内部同步接口，与 Gmail/Calendar/Outlook/Slack 的 OAuth 集成开箱即用。可观测性方面，匿名遥测（packages/telemetry）设计克制且有 allowlist 白名单与 docs/telemetry.md 文档，但这服务于项目方而非企业用户；对运营方有价值的指标（QPS、延迟、错误率、队列深度）无暴露端点，console.log/console.error 是主要日志手段，PRISMA_LOG_QUERIES 仅控制 SQL 调试输出。健康检查仅存在于 Agent 调度器内部，API 层无 /health 端点证据。

小结: Comp AI CRM 的工程实践在"开发期企业就绪"上表现突出——配置规范、CI/CD 自动化、类型安全、并发一致性、认证集成均有较高完成度；但在"运营期企业就绪"上存在明显缺口：授权模型过于简单、无全局审计、无监控告警体系、数据库单点。对于看重快速部署和 AI 能力的创新型团队，当前的运营能力可以接受；但对于受合规约束的中大型企业客户，RBAC、审计合规与高可用是采购决策的硬门槛。该维度得分 6.0/10，构成商业化进程中的可改进项而非根本性障碍。

6.1 最优路径：SaaS 托管服务（推荐优先实施）

路径描述：基于 MIT 协议，直接提供全托管 SaaS 版本，对标 Supabase/Twenty 模式。

可行性依据： - 部署复杂度（三进程 + Postgres + OAuth + 邮件同步）使托管价值凸显，自托管用户有强烈迁移动力； - 付费触发点清晰：agent 运行成本、数据服务按量、运维负担三点均指向托管升级； - 已存在 Context 商业数据集成接口，可立即作为增值付费项。

实施要点： - 建立定价页面与付费墙，区分免费自托管与付费托管功能； - 将 Context 数据服务作为按量计费的增值模块； - 补充应用级容器化与一键部署方案，降低托管成本。

6.2 辅助路径：Open Core 增值功能

路径描述：核心功能保持 MIT 开源，企业级功能（RBAC、审计日志扩展、集群部署、SSO 增强）闭源收费。
