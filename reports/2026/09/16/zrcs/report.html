二、安装部署与使用指南

上手难度等级：🟡 中等（D9 = 5.0/10）——面向有技术基础者

ZRCS 未提供任何一键安装包、容器镜像或云部署模板，落地路径是「安装系统级依赖 → CMake 编译 → 手动按顺序启动多进程」。以下步骤均取自仓库 README 原文，未作任何改写或补充。

1. 环境要求（README 明示）

  • CMake 3.18.1+
  • 支持 C++17 的编译器
  • Protobuf、Boost、Threads
  • 平台：Linux、Windows / MSYS2（README 建议 Windows 优先使用 MSYS2 UCRT64 环境；未提及 macOS）
  • 实时模式额外需要：Xenomai、ethercat_rtdm

2. 安装系统依赖

Linux（原 README 命令，逐行保留）：

sudo apt install libzmq3-dev
sudo apt install nlohmann-json3-dev
sudo apt install libabsl-dev
sudo apt install libprotobuf-dev protobuf-compiler
sudo apt install libboost-dev
sudo apt install qt6-multimedia-dev
sudo apt install libqt6svg6-dev qt6-base-dev
sudo apt install libncurses-dev libncursesw5-dev

Windows / MSYS2（原 README 命令）：

pacman -S mingw-w64-ucrt-x86_64-nlohmann-json
pacman -S mingw-w64-ucrt-x86_64-zeromq
pacman -S mingw-w64-ucrt-x86_64-cppzmq
pacman -S mingw-w64-ucrt-x86_64-protobuf
pacman -S mingw-w64-ucrt-x86_64-opencascade

如需构建 GUI 和打包，README 另建议安装：

pacman -S mingw-w64-ucrt-x86_64-qt6-base
pacman -S mingw-w64-ucrt-x86_64-qt6-svg
pacman -S mingw-w64-ucrt-x86_64-qt6-multimedia
pacman -S mingw-w64-ucrt-x86_64-abseil-cpp
pacman -S mingw-w64-ucrt-x86_64-nsis

注：Eigen3 已内置在 3rdParty/eigen（5.0.0），无需安装系统包。

3. 获取源码与构建

README「快速开始」给出的标准流程：

git clone <your-repo-url> zrcs-dev
cd zrcs-dev

按需选择构建模式（standard / simulation / realtime）：

cmake -S . -B build -DBUILD_MODE=standard
cmake --build build

cmake -S . -B build -DBUILD_MODE=simulation
cmake --build build

cmake -S . -B build -DBUILD_MODE=realtime
cmake --build build

构建产物路径（README 明示）：build/bin/zrcsnrt、build/bin/zrcsrt、build/bin/zrcsgui、build/bin/motiongui。其中 realtime 模式通常只构建 zrcsnrt 和 zrcsrt；非 realtime 模式还会构建两个 GUI。

首次配置 MuJoCo 时，上游 CMake 可能通过 FetchContent 下载 lodepng、qhull、libccd、tinyobjloader、miniz 等依赖；README 给出的跳过方式为配置时添加 -DZRCS_ENABLE_MUJOCO=OFF。

4. 启动与运行

README 推荐的启动顺序：先启动 zrcsnrt，再启动 zrcsgui，需要时再启动 motiongui。通常后端只需手动启动 zrcsnrt，因为它会自动拉起 zrcsrt 子进程。

./build/bin/zrcsnrt
./build/bin/zrcsgui

Windows PowerShell：

.\build\bin\zrcsnrt.exe
.\build\bin\zrcsgui.exe

Linux 下需要放通端口（README 原命令）：

sudo ufw allow 5555
sudo ufw allow 5556

5. 项目配置

当前激活项目由 config/project.txt 指定，仓库内该文件内容为 3axis，即默认从 config/3axis/ 读取 axis.xml、model.xml、ethercat.xml 等配置。仓库已提供 3axis、5axis、demo、single-axis、ur5、hg-5axis、galvo-platform 等示例项目，切换项目通常只需修改 config/project.txt。

6. 可选：测试与 Windows 打包

测试目录为 test/，可见测试目标为 test_spsc、test_command、test_config_manager、test_zmq_comm；关闭测试构建可配置 -Dtest=OFF。

Windows 打包前需以 Release 配置构建：

cmake -S . -B build -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release -DBUILD_MODE=simulation
cmake --build build --target zrcsgui zrcsnrt zrcsrt -j 4

然后运行仓库提供的打包脚本：

bash tool/package/package_installer.sh

7. 部署形态说明

仓库根目录不存在 Dockerfile、docker-compose、Helm Chart 或 K8s 清单（本地实测 has_dockerfile: false，ci_workflows: 0）。素材中出现的 3rdParty/magic_enum/Dockerfile、3rdParty/matplotlib-cpp/contrib/Dockerfile 属于内置第三方组件的自测镜像，与本框架的部署无关。因此 ZRCS 的部署方式为：手工安装系统依赖 → CMake 编译 → 手动按顺序启动 zrcsnrt / zrcsrt / zrcsgui。实时模式还需 Xenomai 实时内核与 EtherCAT 运行环境，属于面向专业运动控制团队的部署形态。

D1.2 痛点真实性与解决程度（1.5/2.5） 痛点真实性高：运动控制的实时性、确定性、轨迹平滑性与多轴同步是设备能否出货的硬约束，绝非"锦上添花"。解决完整度也较高——README 显示已落地 Enable/Disable/Reset/Setmode/MoveJ/MoveL/MoveC/MoveAbsJ/MoveV/ContinuousJog/MoveLGalvo 等命令链路、共享内存无锁队列、ZMQ+Protobuf、Ruckig 限加加速度轨迹、串联/并联/笛卡尔模型 FK/IK、EtherCAT 与虚拟伺服双形态控制器抽象、三构建模式（standard/simulation/realtime）、NSIS 打包脚本，并有 1428 个测试文件、测试占比 23.5%。 扣分点在于需求验证缺位与替代成本极低：4 star / 0 fork / 0 issue / 0 release / 2 位贡献者 / 0 topics，没有任何外部用户反馈、功能请求或采用案例，无法证明"外部用户也认为这是刚需"；同时商用控制器（Beckhoff TwinCAT、Siemens、ACS、固高、Delta Tau）与开源方案（LinuxCNC、ros2_control/ROS 2、OROCOS）已能覆盖大部分需求，README 中亦无任何与替代品的差异化说明（未提及精度/周期/成本对比）。综合判为"方案完整但市场未验证"。

结论

D2 技术成熟度与产品质量得分 5.3 / 10，属「一般」档（达到行业平均线附近，存在明确改进空间），尚不具备商业化交付条件。

核心优势（架构层面）： - RT / NRT / GUI / Common 四层解耦、共享内存通信、10 类机型配置驱动的架构骨架清晰，符合实时运动控制系统的标准设计范式，架构分层是本项目最有价值的资产； - 功能矩阵覆盖较宽（实时控制、轨迹规划、行为树编排与可视化、物理仿真、AI 插件），技术选型（Eigen / MuJoCo / ruckig / BehaviorTree.CPP / Qt / ZMQ）均为成熟工业级组件； - .claude/skills/ 下的 realtime、windows-build、cpp-naming-rules 等结构化知识文件，体现出高于一般早期项目的工程规范意识。

核心风险（成熟度层面）： 1. 项目生命周期极短（创建至最近推送仅 19 天），无 Release / 无 Tag / 无 CHANGELOG，处于 pre-alpha，稳定性、向后兼容性、实时性能均无任何可验证数据； 2. 依赖治理失当：16 个第三方库全量 vendored，且存在大量重复拷贝（zmq.hpp ×5、tinyxml2.cpp ×3、BehaviorTree.CPP ×2、doctest.h 双版本），无 submodule / 包管理器管理，既膨胀仓库又使 CVE 跟踪不可能； 3. 工程流程空白：CI workflows 为 0，无 Dependabot / 静态分析 / PR 模板 / CODEOWNERS，has_dockerfile/has_contributing/has_security_md 全为 false； 4. 文档与测试的真实规模难以确认：表面统计被 3rdParty 自带资产严重稀释，自研文档覆盖与测试覆盖率均无证据支撑； 5. 国际化与部署便利性缺失：无 i18n 框架痕迹、无容器化交付物、运行环境依赖手工配置。

商业化建议：本项目在架构设计上具备可商业化的骨架，但需优先补齐「依赖治理（迁移至 vcpkg/Conan 或 submodule）+ CI 与质量门禁 + 首个语义化版本与 CHANGELOG + 实时性能基准数据 + 容器化交付」这五项工程基础设施，方能将架构优势转化为可交付的产品成熟度。在当前状态下，技术风险主要集中在工程流程而非设计理念。

分析结论

  1. 无容器化、无包管理器、无一键脚本：仓库根目录不存在 Dockerfile / docker-compose / Helm（素材中两个 Dockerfile 均在 3rdParty/ 内，属第三方组件自测镜像），CI workflows 为 0，意味着没有经过持续验证的构建/部署流水线，用户拿到的是「源码 + 文档」而非「可运行的交付物」。
