二、安装（三种方式，任选其一）

方式 1：skills CLI（推荐，一条命令）

npx skills add wheresryan22/anatomy -g

CLI 会询问要为哪些 agent 安装；用 -a 跳过询问：

npx skills add wheresryan22/anatomy -g -a claude-code

可选值：-a claude-code、-a antigravity、-a opencode、-a codex、-a minimax-code。去掉 -g 则安装到当前项目（如 .claude/skills/anatomy）。

方式 2：git clone

git clone https://github.com/wheresryan22/anatomy.git ~/.claude/skills/anatomy

（Antigravity 用 ~/.gemini/antigravity/skills/anatomy，OpenCode 用 ~/.config/opencode/skills/anatomy，Codex 用 ~/.agents/skills/anatomy，MiniMax Code 用 ~/.minimax/skills/anatomy。）

方式 3：ZIP / 一行 curl（macOS、Linux）

mkdir -p ~/.claude/skills/anatomy && curl -L https://github.com/wheresryan22/anatomy/archive/refs/heads/main.tar.gz | tar -xz --strip-components=1 -C ~/.claude/skills/anatomy

三、首次调用

在 Claude Code 中直接说一句话，无需参数、无需配置文件：

Codex 中用 $anatomy；Antigravity、OpenCode、MiniMax Code 用 /anatomy。也可不点名 skill——说"画一张等轴测解释图"它同样会被加载。

技能没出现时：Claude Code 若启动时 skills 目录还不存在，运行 /reload-skills；其他 agent 重启对应 CLI。

五、常见问题

  • Codex 中浏览器自检被沙箱拦截：图仍会生成，仅自检失败。可选：在该命令上批准沙箱外运行（需 approval_policy = "on-request"）；或在 ~/.codex/config.toml 中放开网络与 /tmp 写权限；或自行运行 node scripts/capture.mjs page.html --out shots/page.png。
  • 提升出图质量的三条习惯：说清"要解释的点"并给真实数字（尺寸/计数/速率/阈值）；或直接点名机器对象并说明什么该动；说明交付形态（独立 HTML / 单个 SVG / React 组件）与明暗主题。

  • 数据迁移：无状态、无持久化数据，升级不涉及数据迁移——这是本项最强的一点。CI 中「Committed pages are unchanged」步骤（git diff --stat --exit-code + 空 git status --porcelain）实质是一道构建漂移闸门，防止升级后产出物静默变化，属于轻量但有效的升级保障机制。

结论：对一个零依赖的本地 skill 而言，运维成本处于理论下界；短板仅在「回滚与变更兼容性缺少书面化运维手册」，故落 7–8 档。

维度结论

本维度体现出一个典型的「工具型/技能型」开源项目的企业就绪度画像：运维侧几乎没有负担（零依赖、无状态、语义化发版、构建漂移闸门、CI 全量重建示例），这是它能被 18,544 star 的用户群低成本采用的重要原因；而传统企业采购清单上的 IAM、集群高可用、可观测性三块在其产品形态下不成立，不应被计为缺陷。

真正的商业化短板有两处，且都可修补： 1. 运维/集成文档断层——CHANGELOG 未验证含破坏性变更说明、无回滚流程、kit 未发布为可依赖的 npm 包、无 API reference；企业若要把它嵌进自有渲染管线，采购方会要求这些。 2. 重图形场景缺性能口径——3D 模式仍在 beta，缺帧率/规模基准，企业客户在做端侧性能验收时会要求数据。

若面向企业商业化，优先级建议：发布 kit 为带类型的 npm 包 + OpenAPI 级的 API 文档 → 补「版本兼容与回滚」运维手册 → 给出典型图元数量/帧率的性能基线（复用已有 stress.mjs）。

分析

核心结论：这是一个"安装门槛极低、使用入口极低，但产出成本与深度使用门槛偏高"的 Agent Skill。

D10.1 效用强度

打分: 1.8 / 3（5–6 档，60%）

Anatomy 的使用价值来自「把一段技术概念变成一个可交互的等轴测说明图」。README 明确给出可落地的场景：Next.js 文档插图、博客/落地页解释器、可打印的 A4 技术图（scripts/print.mjs）、React 组件形态。用户拿到的不是一次性截图，而是自己拥有的源码资产——一个 Node 构建脚本加上它生成的页面，或 React 端的几何模块 + 静态服务组件 + 客户端运动组件。

效用真实且不低：一张「240 个实体 + 15 根线缆」带实时读数、可悬停拆解、带几何自审（kit/audit.mjs 证明没有管线穿过任何东西）的图，人工完成需要设计 + 前端 + 校对的多轮往返；技能把它压进一次 agent 会话。产出物还带可打印版、明暗双主题、无 WebGL 时 SVG 仍可读的降级路径。

但它停在「明确但有限」这一档，理由有三：

  1. 效用层级是工具级，不是运行时依赖。它是产出物的生成器，产出物本身才是价值载体；用户不会「持续依赖」它，而是偶发调用一次。
  2. 可替代性不低。同类需求可被 Mermaid / Excalidraw / D3 手写，或直接用通用 agent 提示词产出 SVG 覆盖；Anatomy 的差异在于工艺约束（四色阶阴影、深度排序、几何审计）与自验证闭环，这提升了质量上限，但不改变「可被绕开」这一事实。README 自己承认「无机构可画的概念会出得更弱」。
  3. 效用确定性受外部条件牵制。需要 Claude Code / Antigravity / OpenCode / Codex / MiniMax Code 之一、Node 20.10+、以及 Chrome（自检脚本）；README 明说「它故意很慢」，Raptor 构建要几分钟，3D 全轨道审计 15–20 分钟，3D 模式仍标 beta。产出质量随 agent 与提示词波动。
