D7.1 运维复杂度与升级路径（1.8/3.0）

配置管理方面，本项目采用"声明式设置 + 宿主设置中心整合"的路线。prefs-shared.ts 定义带边界钳制的偏好模型（窗口比例、终端字号等），SideCardSection.tsx 实现注册表驱动的设置 UI，插件设置通过 mergePluginSetting 与宿主 DSH 设置服务合并，端侧设置由 sanitizeState 做容错与状态净化。这一模式对终端用户友好，无需手工编辑配置文件；但项目本身不提供独立于宿主的配置中心或环境变量覆盖通道（DSH_TELEMETRY_DISABLED 仅用于 CI 场景），在需要批量/受控配置的企业环境中灵活性不足。

运维负担上，项目无独立服务进程、无容器化交付（未提供 Dockerfile），作为 Cordis 插件完全寄生在 DSH 宿主进程内，日常"运维"即宿主运维 + npm 包版本管理。但安装链路并非零干预：README 明确记载首次安装会因 pnpm 11 拦截 node-pty 构建脚本失败，需在 ~/.dsh/profiles/web 下手动执行 pnpm approve-builds --all 后重跑安装。虽然该步骤已文档化并有 TerminalDepsBanner 在端侧提示修复命令，仍构成企业环境批量部署时的人力门槛。项目无 CONTRIBUTING、无 CODEOWNERS，也侧面反映运维责任边界尚未企业化。

升级路径存在明显张力：一方面发布工程自动化程度高——release.yml 通过 npm Trusted Publishing（OIDC）发布，自动校验 GitHub Release tag 与 package.json version 一致，并按 prerelease/stable 自动选择 alpha/latest dist-tag，回滚可借助 npm 包版本机制实现（重新安装上一版本即回退）；CI 中另有 plugin-mount 作业将打包产物装入真实 DSH 实例做冒烟验证，兼有 Aggregate double-mount regression 防回归。但另一方面，发布节奏极快：自 2026-08-17 至 2026-08-30 的 13 天内发布 10 个版本（v0.13.0 → v0.18.0-alpha.0），其中包含 alpha 通道对 DSH 0.1.2-alpha.x 的强制适配（README 声明 v0.18.0-alpha.0 起不再支持 0.1.0-rc.8 ~ 0.1.1-rc.2）。这意味着升级必须与 DSH 宿主版本严格对齐，两线（stable/alpha）并行维护增加了企业客户选择与验证成本。仓库内未发现 CHANGELOG 或版本迁移说明文档（release note 依赖 GitHub Release 页面），数据迁移方面主要依赖 localStorage 层的 sanitizeState 对持久化状态做净化与 ID 种子恢复，可容忍轻微 schema 漂移，但缺乏跨大版本的结构化迁移方案文档。

D7.2 安全管理与权限控制（1.5/2.5）

安全设计是该项目代码质量中最突出的部分之一，其纵深防御特征远超典型开源插件：

  • 请求级授权/信任围栏：服务端 src/index.ts 通过 ensureWorkspacePath 做路径穿越防护、isTrustedApiRequest 建立信任围栏、parseLoopbackAllowlist 管理回环地址白名单；Git 操作经 runGit 参数数组传参（杜绝 shell 拼接注入），worktree 目标必须经列表校验。
  • 终端所有权隔离：AgentPtyRegistry.assertOwned 确保代理只能访问本会话创建的 PTY，信号发送走白名单（ALLOWED_SIGNALS），子代理 kill 按钮带二次确认防误操作。
  • 内容安全：HTML 预览强制沙箱 iframe（HTML_IFRAME_SANDBOX 无同源/无顶层导航），Markdown 内嵌 HTML 经 DOMPurify 消毒（postProcessSanitized），Mermaid 采用 strict 安全渲染；e2e 测试专门断言 script 标签被移除。
  • 文件访问边界：文件打开前检查 workspace fence（isWithinWorkspace），围栏拒绝时显示友好提示而非静默失败。

但以企业级安全体系衡量仍有本质缺口：

  • 认证与身份：项目不自带任何用户认证，完全依赖 DSH 宿主的单用户/本地会话模型，不支持 SSO/OAuth/LDAP/SAML，也没有多租户概念。这对面向单人开发场景的 DSH 生态而言是合理的架构选择，但企业客户若需集中身份管理，只能依赖外围网关，无法在插件层满足。
  • 权限模型：现有的围栏/所有权校验属于功能级与资源级访问控制（哪些 API 可调、哪个工作区可读写、哪个 PTY 可访问），而非用户级细粒度 RBAC/ABAC——没有角色、没有策略引擎。
  • 审计日志：仓库内无安全审计模块。虽有 jobs-routes.ts 的作业输出追踪/事件回放、客户端对模型读/写/编辑的实时追踪，但这些服务于产品功能（任务可视化）而非合规审计（谁在何时执行了什么敏感操作）。
  • 数据安全：传输层面走本地回环 HTTP/WebSocket（有回环白名单与协议校验），存储层依赖宿主；密钥管理无涉（不持有凭据），内容层加密/消毒措施较强。

综合判断：若将"安全"理解为对不可信内容与工作区边界的防护，项目已接近 7–8 档水平；但按企业就绪度的认证授权 + 审计 + RBAC 标尺衡量，缺少身份层与审计层是硬性短板。故整体落在"有请求级认证/粗粒度权限、安全机制以纵深防御见长但无完整企业安全体系"的 5–6 档。
