  (cd "$workspace" && bun install --frozen-lockfile)
done

Step 3 — 启动前后端（README 原文，需要两个终端/进程同时运行）：

bun run dev:backend    # API + orchestration on :3201

Step 4 — 自托管部署（README Self-hosting 原文，生产环境）：

SERVER_IP=<host-ip> PG_PASSWORD=... OPENROUTER_API_KEY=... \
  infra/self-host/deploy-app.sh /path/to/this/repo

Step 5（可选）— 团队记忆服务（memory/docker-compose.yml 原文）：

docker compose -f memory/docker-compose.yml up -d

D1.2 痛点真实性与解决程度（2.5 分）

小分: 1.5 / 2.5（即 60% 档）

考察点 分析
痛点真实性 痛点明确且真实：团队级使用编码代理的三大障碍——(1) 多代理碎片化（Claude Code vs Codex vs OpenCode 各自为政）；(2) 代理运行无隔离、凭证暴露在沙箱中；(3) 代理产出（答案 vs 工件）难以进入团队既有工作流（PR/Slack/审批）。这些问题在一周内即获得 284 star 与相对较高的 fork 比例（58 forks，比例 20.4% 远超平均），侧面印证痛点共鸣。
解决完整度 方案架构完整度较高：解决了从调度（run API）、隔离（sandbox 契约）、审计（Postgres 事件溯源）、审批（human-in-loop 卡片）、交付（原生 DOCX/XLSX/PPTX/PDF 工件 + PR）到协作（Slack-native）的全链路。事件化的会话时间线上看是"完整闭环"而非单点工具。
替代成本 替代选择众多但均为碎片化方案：直接用 Claude Code 团队版、各自代理自带 dashboard、或自行用 n8n/自建 runner 拼装（工程成本高）。尚无以 "byok 代理 + 统一控制面 + 工件交付" 为核心的开源整合层主导者。团队若从零自建等价平台的成本显著高于采用本品，但切换到厂商封闭方案（如 ChatGPT Team/Codex Cloud）的成本较低，构成一定威胁。

数据来源: README 详细的功能矩阵（事件契约、agent 适配层、sandbox 契约、typed tools 网关、SKILL.md 导入、Slack 线程内审批）与架构文档的完备程度（81 个文档文件）表明作者对痛点有深刻理解；但开放 issue 仅 1 个且 0 个已关闭 issue，没有用户实际使用反馈的硬数据支撑痛点验证强度。

扣分原因: 项目处于 alpha 状态仅 7 天，替代品数量多（各类 agent 原生平台与编排工具），团队采用决策中"现有工具已够用"的惰性成为最大阻力；开放 issue 极少意味着暂无外部用户的真实痛点反馈作为佐证。

D1.3 市场时机判断（2.5 分）

小分: 2.0 / 2.5（即 80% 档，满分档位 8/10）

考察点 分析
技术成熟度曲线 编码代理（Claude Code/Codex/OpenCode）已越过概念验证期，大量开发团队已将其纳入日常开发流程（README 称 "It already runs real daily workloads"）。"代理编排/多代理治理"层正处在从个人使用到组织落地的爬坡段——恰是为独立控制面/协调层建立标准的窗口期。沙箱技术（Daytona/CubeSandbox）、事件溯源 Postgres、浏览器流（noVNC）等基础组件均已成熟，不存在早期技术不可用风险。
竞争密度 竞争格局尚未固化，但已可见先行者：(1) OpenAI Codex Cloud / Claude Code 团队版等厂商原生工作流（封闭、纵向一体化）；(2) 开源替代集群如 OpenCode 等正在确立个人代理标准；(3) 编排/沙箱类早期玩家（Daytona 等）已进场。横向的中立协调层尚无明显赢家——这是窗口期，也是窗口可能迅速关闭的警钟（若 Claude/OpenAI 开放自身团队级工作流，将挤压中立层的生存空间）。
监管/标准 无直接监管驱动，但企业 AI 治理需求（凭证安全、审计、审批、数据主权）是隐性推动力。AGPL + 商业双授权的模式正好满足企业合规采购路径，self-host 的卖点对应欧盟及金融行业的数据主权趋势。行业事实标准未定（agent 事件契约无统一格式），useAgent 试图通过"canonical event contract"参与定义标准，存在标准占位先机但成功率受生态影响力制约。

数据依据: 项目创建日期为 2026-08-29，属行业窗口期布局；topic 同时覆盖 claude、codex、opencode 三个主流代理说明瞄准多引擎共存生态位。竞争密度依据市场公开竞争格局判断（该品类下已存在 OpenAI Codex Cloud、Anthropic Claude Code 团队版及各类代理编排平台等先行者，但自托管团队级工作流尚无开源主导者）。

考察点 分析
行业覆盖 核心场景为代码与研发交付（PR、测试），天然锚定软件行业；但原生工件层（DOCX/XLSX/PPTX/PDF——设计用于各种业务输出如网站、deck、spreadsheet、报告、市场研究）将其扩展至市场、销售、运营、咨询等知识型团队；Slack 渠道使非工程角色也能触发任务，具备跨部门边缘延伸能力。
场景多样性 非纯横向通用（不像数据库或网络层谁都需要）、亦非纯纵向专用；其形态类似"AI 代理的 PagerDuty + 工单系统"，横跨开发运维（代理调度、审批）、团队协作（Slack、知识库）、内容生产（工件渲染）三大场景。核心路径是"给代理当老板"，可复制到任意愿意把工作交给代理的团队。
可延展性 事件化架构与 provider-neutral 契约决定了可延展性潜力较大：(1) 新增 agent 引擎只需写一个 adapter；(2) typed tools 网关机制可自主接入任意企业内网工具（GitHub/Notion/Linear/HubSpot 已有连接器，模式可复制）；(3) 产物格式已覆盖文档/表格/演示三类通用办公格式，向上可拓展 BI 报告、合同等深度格式；(4) memory/skills/knowledge 体系搭建了组织级能力沉淀的基础。

数据来源: README 明确列出 "Work arrives from anywhere"（Web app/Slack/REST API/schedules）、连接器矩阵（Gmail/Linear/Notion/HubSpot）、工件格式（DOCX/XLSX/PPTX/PDF）、以及 "Workspace surfaces"（知识库/团队记忆/技能/自动化）。Topics 分布集中在 agents/automation 而非单一垂直行业标签，支持多场景判断。

扣分原因: 产品主界面与核心 UX 仍高度围绕"编码/研发任务"设计（沙箱=Linux 工作台、浏览器、repo、终端），虽理论上可用于泛业务自动化，但实际开箱体验的默认场景偏研发；从研发到广义知识工作的跨越需要额外产品化投入，当前评估为多行业可用的 B+ 水平而非基础设施级。

D4.1 协议对变现模式的影响（0.8/2.0）

硬事实：LICENSE 为 AGPL-3.0-only；仓库内存在 COMMERCIAL-LICENSE.md，README 明确说明「若要将 useAgent 嵌入专有软件、在 AGPL 义务之外分发、构建 OEM/白标产品或获取不同条款，可提供商业许可」。

分析：AGPL-3.0 是网络传播型强 copyleft 协议，对第三方将 useAgent 直接包装成云服务或闭源衍生品构成显著约束——这恰好是原厂商业授权的销售驱动力。项目通过「AGPL 社区版 + 商业授权版」的双许可结构，实际打开了一条经典的 MongoDB/MySQL 早期路径：开源版负责获客与生态，商业授权面向需要闭源嵌入、OEM、白标的企业收费。

但需要明确：AGPL-3.0 本身天然封锁了纯 SaaS 托管作为独立第三方变现模式，任何基于修改版的网络服务都必须公开源码；即使是原厂自营 SaaS，也必须依靠自身版权持有者身份进行再许可，法律结构上比 Apache/MIT 复杂得多。协议并非「无约束」，而是「有约束但配套了解锁钥匙」。
