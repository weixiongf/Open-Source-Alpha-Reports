安装部署与使用指南（草稿）

前置条件（素材原文） - Node.js >= 22.5.0（package.json 的 engines.node；README 各平台安装段均标注 "Node.js >= 22.5 (or Bun)"） - 平台侧版本：Claude Code v1.0.33+；VS Code Copilot Chat v0.32+；JetBrains Copilot plugin v1.5.57+ - 形态说明：仓库不提供 Dockerfile / docker-compose / Helm，无容器化部署路径；部署 = npm 全局包 + 各 IDE 的 MCP/hook 配置文件，本地持久化用内置 SQLite（无需外部数据库）

路径 A — Claude Code 插件（官方推荐，最省事）

/plugin marketplace add mksglu/context-mode
/plugin install context-mode@context-mode

重启 Claude Code（或 /reload-plugins）。验证：

/context-mode:ctx-doctor

路由自动生效（SessionStart hook 在运行时注入路由指令，不写入项目文件）。可选状态栏需手动编辑 ~/.claude/settings.json：

{
  "statusLine": {
    "type": "command",
    "command": "context-mode statusline"
  }
}

路径 B — MCP-only（无 hooks 自动路由，适合先试用）

claude mcp add context-mode -- npx -y context-mode

或全局安装后在各客户端注册：

npm install -g context-mode

路径 C — 手工配置（非 Claude Code 平台，以 Gemini CLI 为例） 单文件 ~/.gemini/settings.json 同时注册 MCP server 与四个 hooks（BeforeTool / AfterTool / PreCompress / SessionStart，命令形如 context-mode hook gemini-cli beforetool），重启后 /mcp list 验证；如需完整模型感知再执行：

cp node_modules/context-mode/configs/gemini-cli/GEMINI.md ./GEMINI.md

Cursor / VS Code Copilot / JetBrains Copilot / Copilot CLI / OpenCode 等平台同理，需各自写 mcp.json + hooks.json 并复制 rules/skill 文件。

日常使用 斜杠命令 /context-mode:ctx-stats、/context-mode:ctx-doctor 等；其他平台在对话中直接输入 ctx stats、ctx doctor、ctx index、ctx search、ctx upgrade、ctx insight，由模型自动调用对应 MCP 工具。

自建 / 二次开发

git clone https://github.com/mksglu/context-mode.git
cd context-mode && npm install && npm test

Windows 注意点（素材明示）：install:openclaw 脚本在 win32 下直接报错“OpenClaw install requires bash (Git Bash or WSL)”；Cursor 本地插件在 Windows 需用 robocopy 而非符号链接。

结论

context-mode 落在 D1 良好偏上（8.5/10） 区间：它对应一个真实、高频、且正随 AI 编码智能体爆发而快速扩张的痛点（上下文溢出与会话状态丢失），方案完整度与平台覆盖广度突出（17 个平台、22K stars、110 贡献者、6.5 个月内 10+ 版本迭代、HN #1），并不属于伪需求或自嗨型项目。

主要保留项： 1. TAM 存在天花板与平台吞噬风险——它切的是 AI 编码市场的「上下文/记忆管理」工具层，属十亿美元级成长期细分，而非百亿美元级基础设施；宿主平台原生功能可能压缩其独立生存空间。 2. 替代品众多——宿主 compact、其它 memory MCP、手写脚本均可替代，方案的差异化依赖「跨平台 + 98% 缩减 + 路由约束」的组合体验。 3. 变现路径可见但受许可约束——Elastic License 2.0 禁止第三方托管服务，反向说明其商业模型为自营 Open Core + 托管 Insight 分析订阅，变现距离较近但受平台厂商定价权挤压。 4. 数据置信度：无外部权威市场规模数据，D1.1 为量级估算；README 中「Microsoft/Google/Meta 等团队使用」为带空链接的徽章声明，未获独立验证，不宜作为市场验证依据，故整体置信度记为中。

结论

context-mode 在 D2 维度表现良好（8.0/10），是一套工程成熟度较高的商业化候选组件。其突出优势在于：（1）产品创新性强且痛点明确——以沙箱执行将工具输出压缩约 98% 再回注上下文，配合会话记忆与跨 17 平台路由强制，构成清晰的差异化价值主张；（2）架构模式化程度高——HookAdapter 契约与多层 BaseAdapter 抽象、策略/适配器/模板方法运用得当，核心组件可复用；（3）安全编码扎实——基于 CVE/MITRE 的环境变量清洗、符号链接/路径逃逸防护、参数化查询与无 shell 注入的命令构造；（4）测试与文档体量大——67% 的测试代码占比、三 OS CI、E2E 与基准测试，以及 ADR/平台矩阵等体系化文档；（5）复刻门槛高，构成一定技术护城河。

主要短板集中在工程质量的长尾：若干核心文件严重超长（server.ts >5000 行、cli.ts >1300 行、extract.ts >2000 行）导致职责过载与维护成本上升；平台列表/摘要逻辑存在重复维护；猴补丁 SDK 内部与多处静默吞异常带来脆弱性；版本迭代极其频繁（169 个 patch）叠加 230 个开放 issue，暗示稳定性仍在快速打磨中；同时缺少自动安全扫描与覆盖率/静态分析门禁，运行环境要求 Node ≥22.5 且依赖原生扩展（better-sqlite3）。这些不构成根本性障碍，但会在规模化商业交付中转化为维护与支持成本。综合判定：高于行业平均、无明显致命短板，可直接支撑商业化交付，建议优先偿还核心大文件拆分与技术债治理。

法律合规与知识产权维度得分 5.9/10，属于"一般偏弱"，构成中等强度的商业化障碍——且障碍集中在两个方向明确的单点上，而非全盘性风险。

  1. 最硬的约束是协议，不是依赖。 ELv2 明确禁止第三方以托管/管理服务形态提供本软件，LICENSE 文件中还存在 license key 反绕过与版权声明保留条款。这直接封锁了 SaaS 变现路径，并使"社区 fork 后自行构建分发"在法律上不可行。同时，ELv2 非 OSI 认证协议，会削弱在部分企业与发行版生态中的可获得性。正面看，内部使用、嵌入自研产品、修改再分发、软件销售、企业支持与双协议等路径仍合法，协议文本本身清晰无歧义，不存在版权归属混乱或无协议状态。
  2. 依赖链干净。 8 个运行时直接依赖全为 MIT/ISC/BSD 类宽松协议，无 GPL/AGPL 传染，对 12.6 万行项目而言依赖面很窄；短板是传递依赖未完整审计、CI 无 license 扫描护栏。

  4. 落地的合规动作建议（供后续人工尽调）：(a) 委托律师就 ELv2 的托管服务禁令边界出具意见，特别是"substantial set of features"的解释范围；(b) 补齐 CLA 或 DCO 并在 CI 中强制，作为所有后续贡献的准入条件；(c) 对 110 位历史贡献者的补签可行性做评估（若双协议是既定路线，越早越好）；(d) 完成 "context-mode" 名称在主要司法辖区的商标检索与核心技术 FTO 分析；(e) 在 CI 中接入 license-checker / SBOM 生成，形成自动化合规护栏。

六、商业路径分析

6.1 主路径：Open Core + 自营托管 SaaS（推荐）

依据：D4.1 显示 ELv2 明文禁止第三方托管但允许版权人自营；D4.2 得分 2.8/3.5，已存在落地商业载体 ctx-insight 托管仪表盘；D4.4 得分 1.6/2，增值空间与定价锚点清晰。

路径设计： - 免费层：个人开发者保留全部核心能力（98% context 压缩、跨会话记忆、11 个 MCP 工具、17 平台路由），维持社区势能与分发广度。 - 付费层（组织级）：以 ctx-insight 仪表盘为载体的组织可见性与治理能力——README 中已成体系的企业安全/治理能力（permissions deny/allow、项目边界隔离、SSRF/IMDS 阻断、密钥脱敏、CTX_FETCH_STRICT 面向 shared service）具备切分企业版素材。 - 定价锚点：statusline 直接展示 "$ saved"，可做 ROI 定价；大组织 $10K+/年客单价有品类先例（GitLab/Elastic/Supabase）。

关键前提：需补齐 Dockerfile（当前无自托管企业分发形态）、公开定价页与企业版功能清单。

6.2 备选路径：企业自托管授权

依据：D7.1 显示本地 MCP/CLI 工具无服务端部署、运维负担天然极低；D7.2 显示安全引擎本身较强（deny>ask>allow 策略、链式命令拆分、路径逃逸防护、基于 CVE/MITRE 的 env denylist、Zod 参数校验）。

路径设计：面向对数据外流敏感的企业，提供自托管企业版授权（含 SSO/OAuth/LDAP/SAML、用户级 RBAC、静态加密、正式审计日志）。当前这些能力均缺失（D7.2 得分 1.5/2.5），需先补齐。

6.3 临界画像下的备选路径（影响力变现）
